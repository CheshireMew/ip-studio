# 离散状态式 2D 动态角色生产方法

在 `SKILL.md` 已确认用户要把锁定角色用于游戏、应用界面、网页、状态式吉祥物或其它逐帧 2D 环境后读取本文件。它负责把真实运行方式变成动作合同，再完成整表生图、切帧、透明处理、预览、打包和消费验证。角色身份仍由 `character-profile.json` 与其中登记的单张主参考图决定。

## 1. 动态合同来自运行环境

不要先列“角色通常需要的动画”。先沿真实链路查四件事：

1. **状态生产者**：玩家输入、AI、日程、应用状态或页面事件究竟会发出什么状态。
2. **方向生产者**：是否存在方向，来自移动输入、目标位置、指针还是根本没有方向。
3. **结果发生点**：哪些动作只是画面反馈，哪些动作要在特定帧通知耕种、攻击、交互、提交或其它系统。
4. **消费者与可见结果**：哪个节点、组件或加载器读取图片，锚点、图集、播放方式和用户最终看到什么。

项目代码存在时直接读取这些生产者和消费者，不能用设计文档中的愿望替代当前程序。只有平台协议时读取正式协议。两者都没有时，依据用户明确用途建立最小但完整的合同；只有会改变状态、方向、尺寸、节奏或输出格式的未知项才询问用户。

角色职责会显著改变合同：

- 日程 NPC 可能只需几个方向静态图；所在位置、场景道具、提示和对白已经能表达活动时，不为每项生活内容制造循环动画。
- 玩家角色只生产控制器真实触发的移动、交互和工具动作；停止时可以保留最后方向的一张静态图，不默认增加呼吸循环。
- 前向应用角色可能只有待机、倾听、说话、处理、成功和失败状态，不需要四方向。
- 固定平台按对应平台适配器的正式状态与布局生产，不把平台数字扩散到其它场景；最终结果是宠物包或安装时交给 `$pet-studio`，Motion Studio 只提供共享动作合同和确定性生产能力。

方向切换不是转身动画。运行时直接切换 `walk-left` 与 `walk-up` 时，只需要两个方向 clip；只有状态机真的播放“从左转到上”的过渡，才建立 `transition` clip。把四个方向循环依次播放只是一种一致性预览，不能标成转身动画或进入运行时。

## 2. 合同结构

Agent 运行：

```text
python scripts/motion_kit.py schema
python scripts/motion_kit.py draft --motion-id <slug> --display-name <name> --output <contract-path>
```

然后根据真实证据完成合同，不让用户手填。主要部分是：

- `target`：使用表面、运行时、角色职责、镜头、状态来源、方向来源、消费者和最终可见结果。
- `canvas`：单格尺寸、锚点、角色安全范围、与角色色板分离的幕布色、正式格式和无损预览格式。
- `clips`：每个运行时 clip 的状态、方向、类型、帧数、逐帧时长、可见语义和效果事件。
- `groups`：哪些 clip 必须在同一张图片中生成，每一格对应哪个 clip 的哪一帧，以及按等分网格还是按透明前景投影识别实际格位。

四种 clip 类型承担不同含义：

- `static`：一张方向或情境姿势，不播放循环。
- `loop`：持续状态，首尾应能自然连接。
- `oneshot`：准备、动作发生和恢复组成的一次动作。
- `transition`：只有运行时存在独立状态过渡时使用。

不要先规定所有动作统一六帧或八帧。循环帧数由步态、呼吸或状态变化决定；单次动作先写关键阶段，再补足看清力度和节奏所需的中间帧。工具或玩法动作通常需要“准备—施力—接触—恢复”，效果事件登记在视觉接触成立的那一帧。运行时在事件帧产生结果，不能点击后立刻改变世界而动画随后补演。

一个 group 是一次完整生成单元。同一动作的全部方向与帧优先放在一张固定网格中；画布过大时可以按动作拆成多个 group，但不能按单帧拆分，也不能让同一方向家族分别生成后再靠缩放和拼接补一致性。

## 3. 从锁定角色建立运行目录

运行：

```text
python scripts/motion_kit.py prepare <kit-folder> --contract <contract-path>
python scripts/motion_kit.py check <run-folder> --stage prepared
python scripts/motion_kit.py ready <run-folder>
```

`prepare` 验证角色包和合同，把角色档案、主参考图与合同快照写入运行目录，并为每个 group 生成提示词、固定网格辅助图和有序图片输入。每个 job 都标记 `requires_user_confirmation: true`；运行 `ready` 后读取本批实际提示词和全部图片输入，完整展示给用户并停止。只有用户确认后，下一轮才原样生成；重试提示词同样重新确认。运行目录位于：

```text
<character-kit>/derivatives/motion/<motion-id>/runs/rNNN/
```

主参考图负责身份，网格辅助图只负责格数、间距和脚底位置。辅助图上的线、基准标记和颜色不能进入成图。存在针对动作、手部、配件或三视角的有效角色校准板时，只有当前 group 确实涉及对应失败才加入；它不能替代主参考图。

## 4. 整表直生图

每个 group 只接受一张包含全部规定格子的完整结果。这里的方向、格数、动作阶段、幕布和运行时语义属于真实消费者要求，可以进入提示词；完整角色档案、用途解释和与当前 group 无关的状态不得进入。获确认后生成时锁定：

- 同一脸型、头身比、身体结构、服装层级、配色与固定配饰；
- 同一镜头和表观尺度；
- 每格一个完整角色，身体、工具和连接配件不跨格、不裁切；
- 方向语义、动作顺序、左右脚或施力阶段；
- 与角色色板分离的平坦幕布；
- 无文字、网格、阴影、场景、速度线、动作弧、跨格残影和临时道具。

不要先生成一张“完美基准帧”，再把它的脸、眼睛、头发、手脚或服装局部贴进其它帧。不同生成图的线条、明暗、五官和内部结构并不完全兼容，局部拼接可能减少位置晃动，却会造成更明显的脸部和肢体变形。允许直生图存在轻微内部变化；无法接受的错误整帧或整组重生，或者从整张动作表进行一致的图像编辑。

同一角色具有左右不对称发饰、衣襟、肩袋、纹样、工具握持或光向时，不直接镜像另一方向。只有镜像不改变任何身份和动作含义时才可以确定性派生，并记录依据。

## 5. 接受、切帧和稳定

实际以最终显示尺寸打开整表，检查身份、方向、动作顺序、帧数、完整身体、表观尺度、脚底、工具连接和幕布。通过后运行：

```text
python scripts/motion_kit.py accept-sheet <run-folder> \
  --job <group-id> \
  --source <generated-sheet> \
  --qa-note <visible-evidence>
```

脚本把整表作为唯一图片生产者，按合同切格。布局严格等分时使用 `equal-grid`；生成器保留了完整行列但使格间距略有偏差时使用 `content-projection`，从抠图后的前景投影找出准确行列边界。投影必须恰好识别合同要求的行列数，否则失败，不能猜少了哪一格。透明处理从整张图边缘和幕布色族建立软遮罩，在预乘 Alpha 空间缩放并清理不可见 RGB，不能只删除精确 RGB，也不能把生成器画出的棋盘格当透明。

两种注册方式分别用于不同运动：

- `bottom-center`：对完整人物使用同一个缩放比例，并以脚底或底座做整数像素对齐。适合静态方向、行走和脚底固定的工具动作。
- `source-grid`：保留人物在源格中的相对位置，只对完整格子做等比缩放和居中。适合跳跃、漂浮或必须保留垂直位移的动作。

确定性稳定只处理完整人物或完整格子。禁止拉伸单个身体区域、仿射扭曲人物、用另一帧替换内部像素、重建脸部或把若干部件重新拼成角色。处理报告必须明确 `internal_pixel_replacement: false`；共享缩放、刚性位移、源图哈希、透明残留、逐帧路径和无损预览都会被记录。

已经接受的 group 后来发现方向、动作或身份错误时，重新生成完整 group，并增加：

```text
--replace-complete
```

旧产物进入 `history/job-replacements/`，新旧帧不能混合。处理失败的候选进入失败历史，不标记完成。

## 6. 预览不是运行时格式

正式运行时使用透明 PNG 图集或透明 PNG 逐帧文件，准确格式由合同决定。颜色和连续性检查使用：

- APNG：逐帧 RGBA 验收，颜色与透明度可直接核对。
- 无损 WebP：体积较小的无损循环预览。
- GIF：只有用户明确要临时分享时转换。它受 256 色调色板限制，出现色差是格式本身的结果，不能承担颜色验收，也不能直接进入正式运行时包。

每个方向 clip 单独预览。需要比较四方向时，用四格同时播放的 QA 画面或分开的四个循环；不要把上下左右依次串成一个 GIF 后称为转向。真正的转身必须有独立合同、方向起点和终点、时长与运行时触发。

## 7. 视觉与语义检查

先检查整表，再检查逐 clip 循环和正式图集：

1. **身份**：每格是否仍是主参考图中的同一角色。
2. **角色职责**：是否只生产合同所需状态，没有为静态 NPC、无方向界面或不存在的功能追加动作。
3. **方向**：前后左右由头顶、脸、身体、服装遮挡和配件位置共同成立；不能只移动瞳孔冒充整人朝向。
4. **动作语义**：步态交替，待机克制，单次动作阶段清楚，状态之间不会混淆。
5. **事件时机**：效果帧与工具、手或身体真正接触目标一致。
6. **连续性**：尺度、锚点、连接件、工具长度和基线稳定，循环首尾没有明显跳变。
7. **透明与颜色**：深色、浅色和高反差底上都没有幕布彩边、透明孔洞或不可见 RGB 污染。
8. **技术完整**：帧数、时长、图集格子、manifest 路径和哈希与合同一致。

轻微直生图晃动只有在最终尺寸明显干扰阅读或碰撞感时才失败。不要为了追求逐像素静止而破坏已经自然的脸部、衣褶和步态。若同一问题连续出现两次，先检查合同、网格、镜头或角色结构是否含糊，再决定重生；不要无限追加负面词。

## 8. 打包与真实消费

全部 group 通过后运行：

```text
python scripts/motion_kit.py finalize <run-folder>
python scripts/motion_kit.py check <run-folder> --stage final
```

正式包包含：

```text
<run-folder>/package/<motion-id>/
├── motion-contract.json
├── motion-manifest.json
├── atlases/
└── frames/
```

manifest 保存目标合同、clip 语义、方向、帧时长、事件、图集和逐帧哈希。APNG、无损 WebP、提示词、整表源图和 QA 报告留在运行目录，不混进运行时包。

用户只要素材时，到正式包检查通过即可。用户要求接入项目时继续验证完整链路：真实状态生产者发出状态与方向，运行时从 manifest 选择 clip，正式帧被消费，事件帧通知目标系统，最终画面在实际尺寸中可见。不得从测试端直接写“正在行走”“已经命中”等消费状态来绕过正在验证的生产者。

固定平台可以在这套共同方法之上增加自己的适配合同，但平台状态、布局和安装不进入 Motion Studio 的通用默认。宠物平台的状态、方向、图集和安装由 `$pet-studio` 的对应适配器负责。
